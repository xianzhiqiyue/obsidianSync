# Obsidian Sync 项目 SOP

## 1. 项目画像

- 项目名称：`Obsidian Sync (Self-hosted)`。
- 项目定位：面向个人或小团队的自托管 Obsidian 多端同步系统。
- 产品类型：Obsidian 插件 + 后端同步服务 + 管理后台 + 运维脚本的综合性同步平台。
- 目标用户：需要自主管理同步数据、希望规避网络不稳定或订阅限制的 Obsidian 用户与维护者。
- 核心场景：
  - 多设备同步同一个 Vault。
  - 弱网、断网、并发编辑后可恢复同步。
  - 服务端历史数据、备份、恢复与审计管理。
- 当前阶段：MVP 到 Beta 强化阶段，已具备同步 API、插件、基础运维与管理后台骨架。
- 复杂度等级：跨模块产品，涉及客户端状态、服务端一致性、数据库迁移、对象存储、部署运维与数据安全。
- 数据敏感性：高。Vault 内容可能包含私人笔记、附件和历史版本，默认按敏感数据处理。

## 2. 子项目边界

| 子项目 | 路径 | 职责 | 主要验证 |
| --- | --- | --- | --- |
| Obsidian 插件 | `apps/obsidian-plugin` | 本地 Vault 扫描、同步计划、冲突处理、重试、用户设置入口 | `npm run --workspace @obsidian-sync/plugin test`、`npm run --workspace @obsidian-sync/plugin typecheck` |
| 同步服务 | `apps/sync-api` | 鉴权、Vault 管理、同步提交/拉取、对象存储、迁移、指标 | `npm run --workspace @obsidian-sync/sync-api test`、`npm run --workspace @obsidian-sync/sync-api typecheck`、`scripts/smoke-api.sh` |
| 管理后台 | `apps/admin` | 服务器历史数据管理、同步事件审计、运维入口的前端子项目 | `npm run --workspace @obsidian-sync/admin typecheck`、`npm run --workspace @obsidian-sync/admin build` |
| 共享包 | `packages/shared` | 跨插件、后台、服务端复用的类型、常量和协议定义 | `npm run --workspace @obsidian-sync/shared typecheck` |
| 基础设施 | `infra` | Docker Compose、监控、Grafana/Prometheus 配置 | `docker compose ... config`、监控栈启动检查 |
| 脚本 | `scripts` | 部署、回归、压测、备份恢复、Beta 发布自动化 | 相关脚本 dry-run 或目标脚本执行结果 |

边界规则：
- 插件不得直接依赖服务端内部实现，只通过公开 API 与共享协议交互。
- 管理后台不得绕过服务端鉴权直接访问数据库或对象存储。
- 服务端数据库 schema 变更必须通过 `apps/sync-api/migrations` 管理。
- 跨子项目请求/响应类型优先沉淀到 `packages/shared`，避免重复定义协议。

## 4. 任务分级与流程

| 等级 | 适用范围 | 必要产物 | 最低验证 |
| --- | --- | --- | --- |
| L0 小修 | 文案、样式、局部脚本、小范围 bug | 变更说明 | 相关 typecheck、单测或人工检查 |
| L1 常规功能 | 单一子项目内可逆功能 | 简短需求/验收点、实现计划 | 目标子项目 typecheck + 相关测试/构建 |
| L2 跨模块变更 | 插件 + 服务端、服务端 + 管理后台、协议变化 | 更新需求/API/测试计划，必要时补设计说明 | 全局 typecheck、相关单测/集成/构建、API 冒烟 |
| L3 数据/安全/生产风险 | 迁移、鉴权、权限、备份恢复、发布回滚、历史数据管理 | 需求、设计、测试计划、运维/回滚说明 | 迁移演练、回归脚本、备份恢复或灰度门禁证据 |

流程：
1. 明确问题、用户、范围、非目标和验收标准。
2. 检查并更新对应主文档，避免只改代码不改契约。
3. 按任务等级选择最小可逆实现路径。
4. 先锁定现有行为：补测试、脚本验证或记录可接受的验证缺口。
5. 实现时保持小 diff，优先复用现有模式和工具。
6. 运行验证，读取输出后再声明完成。
7. 总结变更文件、验证证据、风险和后续事项。

## 5. Definition of Ready

任务进入实现前应满足：
- 已明确目标用户或维护者场景。
- 已明确范围、非范围和验收标准。
- 已识别受影响子项目、数据模型、API、部署或安全边界。
- 对 L2/L3 任务，已有对应文档更新计划或设计说明。
- 对生产或数据风险任务，已有回滚、备份或演练路径。

允许带着已标注的未知项开始 L0/L1 任务；不得在未知项会影响数据安全、权限模型、公开 API 或迁移策略时直接实现。

## 6. Definition of Done

任务完成必须满足：
- 代码、配置、脚本和文档均已更新到同一事实口径。
- 相关自动化验证已通过，或明确记录无法运行原因和替代检查。
- 没有遗留未解释的类型错误、测试失败或构建失败。
- 新增接口、命令、环境变量、迁移或发布步骤已写入对应文档。
- 数据、安全、生产相关变更包含回滚或恢复说明。
- 最终说明包含：变更摘要、验证证据、已知风险、后续建议。

## 7. 验证门禁

常用命令：

```bash
npm run typecheck
npm run build
npm run test
```

按场景追加：

```bash
npm run --workspace @obsidian-sync/plugin test
npm run --workspace @obsidian-sync/admin build
scripts/smoke-api.sh
scripts/regression-sync-api.sh
scripts/drill-backup-restore.sh
scripts/pre-beta-check.sh
```

门禁规则：
- 插件同步逻辑变更至少运行插件单测和插件 typecheck。
- 服务端同步协议、鉴权、迁移变更至少运行服务端 typecheck、服务端测试或 API 冒烟。
- 管理后台变更至少运行后台 typecheck 和 build。
- 共享协议变更必须验证所有受影响 workspace。
- 发布前必须走 `scripts/pre-beta-check.sh`，必要时追加压测和灰度门禁。

## 8. 数据、安全与权限规则

- Vault 内容、对象哈希、历史版本、设备 token、数据库备份默认视为敏感信息。
- 不在文档、日志或测试快照中写入真实密钥、真实 token、真实用户私密内容。
- `.env`、`.secrets`、备份文件和生产凭据不得提交。
- 管理后台所有数据管理能力必须经服务端鉴权和权限校验。
- 删除、批量归档、历史版本清理、恢复覆盖等破坏性能力必须提供预览、确认、审计记录和回滚/备份策略。
- 数据库迁移必须可重复执行，并说明向前/向后兼容影响。
- 历史版本和删除墓碑默认保留三个月；缩短保留期属于数据风险变更，必须先更新需求、运维和测试口径。

## 9. 发布、回滚与运维

- 日常部署和回滚遵循 `docs/部署与运维手册.md`。
- Beta 发布遵循 `docs/Beta发布手册.md`。
- 发布前检查包括构建、测试、API 回归、指标阈值和必要的备份状态确认。
- 回滚优先回滚应用版本；涉及数据库迁移时必须先确认兼容性和恢复点。
- 任何生产故障处理都应保留日志、指标、命令和结论，必要时回填到运维手册或故障记录。

## 10. 当前已知缺口

- 管理后台目前是前端骨架，尚未定义管理 API、权限模型和历史数据操作审计表。
- `packages/shared` 仍较轻，跨子项目协议类型需要逐步收敛到共享包。
- 服务端集成测试依赖环境变量和外部依赖，部分场景可能只能在具备 PostgreSQL/S3 的环境中完整运行。
- 历史版本清理、归档、恢复覆盖等高风险管理能力尚缺少详细需求和回滚设计。

## 11. 新需求处理模板

处理新需求时，在实现前至少写清：

```text
目标：
用户/维护者场景：
范围：
非范围：
受影响子项目：
数据/权限/部署影响：
验收标准：
验证命令：

```

小型任务可把上述内容压缩到提交说明或任务总结；L2/L3 任务应落到需求、计划、测试或设计文档中。
