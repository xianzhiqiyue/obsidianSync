# Obsidian 自建同步系统架构设计（v1）

## 1. 设计目标
- 让 `macOS / Windows / Android` 端在弱网和并发场景下稳定同步。
- 采用“可演进”的分层架构：先保证正确性与恢复能力，再优化实时性。
- 将“文件内容”和“同步元数据”解耦，降低后续扩容与迁移成本。

## 2. 总体架构

```text
+--------------------+      HTTPS       +------------------------+
| Obsidian Plugin    | <--------------> | API Gateway / Sync API |
| (Desktop/Android)  |                  +-----------+------------+
+---------+----------+                              |
          |                                         |
          | local queue/state                       |
          v                                         v
+--------------------+                 +-------------------------+
| Local Vault Files  |                 | Auth + Sync Services    |
+--------------------+                 +-----+-----------+-------+
                                            |           |
                                            |           |
                                            v           v
                                   +----------------+ +------------------+
                                   | PostgreSQL     | | Object Storage   |
                                   | metadata/state | | (S3-compatible)  |
                                   +----------------+ +------------------+
```

## 3. 核心组件职责

| 组件 | 职责 |
| --- | --- |
| Plugin Sync Engine | 扫描本地变更、拉取远端变更、冲突处理、重试控制 |
| Plugin Local State | 保存 checkpoint、文件版本映射、失败队列 |
| API Gateway | 统一鉴权、限流、请求日志、路由 |
| Auth Service | 用户创建、登录、设备注册、token 刷新、登出、设备撤销 |
| Sync Service | 变更校验、版本推进、冲突检测、提交事务 |
| Metadata DB | 存储 Vault/文件/版本/变更日志/tombstone |
| Object Storage | 存储文件内容对象（按 content hash 去重） |
| Observability | 指标、日志、告警、审计记录 |
| Admin Portal | 查询服务端历史数据、预览并发起恢复/删除/指定当前版本等受控管理操作 |
| Admin Operations | 管理后台操作的服务端执行层，负责权限校验、事务提交、审计和同步事件生成 |

## 4. 关键流程

### 4.1 首次同步
1. 客户端获取本地扫描结果并判断 vault 是否为空。
2. 用户显式选择 `Upload-First` 或 `Download-First`。
3. 服务端记录初始 checkpoint，禁止未决策略下自动双向同步。

### 4.2 增量同步（单次循环）
1. 客户端上传本地变更摘要（file_id/path/op/base_version/content_hash/operation_time_ms）。
2. 服务端校验 base_version（CAS）。
3. 对通过校验的变更发放上传地址（仅对缺失 object）。
4. 客户端上传对象并提交 commit。
5. 服务端事务化写入变更、推进版本、返回新 checkpoint。
6. 客户端按 checkpoint 拉取远端变更并应用本地；单个 checkpoint 是不可拆分的分页单元。

### 4.3 冲突处理
1. CAS、路径占用或删除墓碑校验失败时返回结构化冲突。
2. 默认策略按 `operation_time_ms` 执行最后操作优先；时间相同则远端获胜，保证决策确定性。
3. 本地删除以持久化 marker 表示，只有同一删除操作提交成功后才能清除；远端旧事件不得清除更新的 marker。
4. 无法可靠判定时生成冲突副本或进入待决状态，不直接覆盖本地内容。

### 4.4 基线与快照
1. `sync/snapshot` 在 checkpoint 共享锁内返回活动文件 manifest、持久删除证据与对应 checkpoint。
2. 快照条目标记为“尚未在本地落盘”，不能因本地缺失而推断为删除。
3. 基线重建直接按最终 manifest 对账：远端获胜或本地缺失时下载，较新的本地操作保留并进入下一轮提交。


### 4.4 管理后台恢复与版本指定
1. 维护者在管理后台选择 Vault，并按路径、文件 ID 或删除状态定位目标文件。
2. 管理后台调用服务端管理接口读取 `file_entries`、`file_versions`、`tombstones` 与 `change_events` 的聚合视图。
3. 维护者选择“恢复误删”“指定历史版本为当前版本”或“软删除”，服务端先返回操作预览。
4. 维护者确认后，服务端在同一事务中锁定 Vault checkpoint 与目标文件，创建管理来源 changeset，写入新 file_version、change_event、admin_operation，并推进 checkpoint。
5. 服务端提交事务后发布 checkpoint 通知；在线客户端尽快 pull，离线客户端上线后补齐。
6. 客户端按同步协议应用管理事件；若本地存在未提交修改，仍走冲突副本保护，不静默覆盖本地编辑。

## 5. 数据架构

### 5.1 关键实体
- `vaults`：Vault 基本信息与拥有者。
- `devices`：设备注册信息与状态（active/revoked）。
- `refresh_tokens`：refresh token 哈希、设备归属、过期与撤销时间。
- `file_entries`：逻辑文件（file_id、current_path、head_version、deleted_at）。
- `file_versions`：历史版本（version、content_hash、author_device、operation_time_ms、created_at）。
- `changesets`：一次提交的变更集合（checkpoint、device_id、status）。
- `tombstones`：删除墓碑（file_id、path、operation_time_ms、deleted_at、expire_at）。

### 5.2 一致性策略
- 元数据变更使用数据库事务提交。
- 对象存储写入先于 metadata commit。
- commit 失败时对象可保留，后续由 GC 回收孤儿对象。
- 同一路径的 create 必须晚于有效墓碑；prepare 与 commit 都执行该校验。
- `change_events` 使用 `(checkpoint, event_index)` 稳定排序，拉取分页不得拆分同一 changeset。


### 5.3 管理后台历史数据模型补充
- `admin_operations`：记录管理后台发起的恢复、软删除、指定当前版本等操作，包含操作人、原因、操作前后状态、关联 changeset 与执行结果。
- `changesets.source`：建议区分 `device` 与 `admin`，避免把管理操作误判为某个客户端提交。
- `change_events.source` / `admin_operation_id`：建议在同步事件中保留来源，便于客户端展示和审计追踪。
- 管理操作不得直接修改 `head_version` 后结束，必须同时维护 `file_versions`、`change_events` 与 `vault_sync_state`。

## 6. 部署拓扑

### 6.1 单机部署（MVP）
- `nginx`（TLS 终止）+ `sync-api` + `postgres` + `minio`。
- 使用 Docker Compose 管理，便于快速上线和备份。

### 6.2 可扩展部署（生产）
- API 无状态化，多副本水平扩容。
- PostgreSQL 主从或托管服务。
- 对象存储切换到托管 S3 或分布式 MinIO。
- 可选 Redis 缓存热点元数据与短期 token 黑名单。

## 7. 安全架构
- 强制 HTTPS，拒绝明文 HTTP 请求。
- access token 短有效期，refresh token 可撤销且轮换；数据库只保存 refresh token 哈希。
- 每个 Vault 使用独立逻辑密钥域，避免横向访问。
- 生产环境公开自助注册默认关闭；受控注册通过环境变量或 bootstrap token 管理。
- 密码修改会撤销其他设备 refresh token，降低凭据泄露后的横向风险。
- 审计日志记录关键操作：登录、设备注册、设备撤销、批量删除。

## 8. 可观测性设计
- 指标：
  - `sync_success_rate`
  - `sync_request_p95_ms`
  - `conflict_rate`
  - `retry_exhausted_count`
- 日志：
  - 请求日志（trace_id）
  - 同步日志（vault_id、device_id、checkpoint）
  - 错误日志（stack + request context）
- 告警：
  - 5 分钟错误率 > 5%
  - P95 延迟持续高于阈值
  - 对象存储写入失败率异常

## 9. 可靠性与恢复
- 每日自动备份 PostgreSQL（全量 + WAL/增量）。
- 对象存储开启版本化或定期快照。
- 每月至少 1 次恢复演练，验证 RPO/RTO。
- tombstone 保留期默认 90 天，支撑误删恢复。

## 10. 技术选型建议
- 服务端：`Go`（并发与部署简单）或 `Node.js + TypeScript`（生态丰富）。
- 数据库：`PostgreSQL 16+`。
- 对象存储：`MinIO`（自建）或云厂商 S3。
- 网关与 TLS：`Nginx` 或 `Caddy`。

## 11. 风险与缓解
- 风险：移动端后台限制导致同步中断。  
  缓解：前台触发优先 + 失败重试 + 明确用户提示。
- 风险：并发冲突高。  
  缓解：CAS + 冲突副本 + 冲突指标监控。
- 风险：误删扩散。  
  缓解：tombstone + 回收延迟 + 快速恢复流程。
