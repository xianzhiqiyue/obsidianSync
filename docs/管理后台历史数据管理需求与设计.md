# 管理后台历史数据管理需求与设计

## 1. 背景

当前同步系统在开发、调试和多端同步过程中，可能因为客户端实现缺陷、误操作、冲突处理不完善或删除传播异常，导致本地 Vault 出现误删除、错误覆盖、历史版本不可见等问题。

本阶段管理后台的核心目标不是做通用 CMS，而是提供一套面向 Obsidian 同步数据的“服务端事实管理”能力：让维护者可以查看服务端数据库中的文件、版本、删除墓碑和同步事件，并通过受控操作把正确版本重新定义为当前版本，再通过同步机制推送到各个客户端。

## 2. 目标

- 支持按 Vault、路径、文件 ID、时间范围查询服务端文件状态和历史版本。
- 支持识别误删、异常覆盖、重复路径、冲突副本和长期未同步设备等风险线索。
- 支持软删除、恢复、指定历史版本为当前版本。
- 支持生成新的服务端变更事件和 checkpoint，让各客户端通过现有 pull 机制获得修复结果。
- 历史版本与删除墓碑默认保留三个月，后台需要展示保留策略和可恢复状态。
- 支持高风险操作预览、确认、审计和回滚线索。

## 3. 非目标

- 不直接修改用户本地文件系统；所有客户端变更必须通过同步协议下发。
- 不绕过服务端鉴权和权限模型直接从管理后台连接数据库。
- 不在本阶段实现文件内容在线编辑器；优先支持查看元数据、下载历史版本和选择版本恢复。
- 不做硬删除对象内容；历史对象清理需要单独的生命周期策略和备份确认。
- 不承诺实时强推到离线客户端；离线客户端上线后通过 checkpoint 增量拉取。

## 4. 角色与权限

| 角色 | 权限范围 |
| --- | --- |
| Vault 拥有者 | 管理自己 Vault 的文件历史、恢复和软删除操作 |
| 系统管理员 | 查看系统级统计、处理跨 Vault 运维问题，不能默认查看明文内容 |
| 审计只读角色 | 只读查看操作记录、同步事件和版本元数据 |

权限规则：
- 所有管理接口必须复用服务端鉴权，并校验 Vault 所属关系或管理角色。
- 读取文件内容或生成下载地址应单独记录审计事件。
- 删除、恢复、指定当前版本、批量操作必须要求二次确认和原因说明。

## 5. 核心概念

| 概念 | 说明 | 现有模型 |
| --- | --- | --- |
| 当前文件 | `file_entries` 中未删除且由 `head_version` 指向的逻辑文件 | `file_entries.current_path`、`head_version`、`deleted_at` |
| 历史版本 | 文件每次 create/update/delete/rename/move 形成的版本记录 | `file_versions` |
| 删除墓碑 | 删除事件的保留记录，用于阻止旧设备复活文件 | `tombstones`、`file_entries.deleted_at` |
| 同步事件 | 客户端 pull 的事实来源 | `change_events` |
| checkpoint | Vault 级增量同步位置 | `vault_sync_state.latest_checkpoint` |
| 管理操作 | 由后台发起的受控修复或删除动作 | 需要新增 `admin_operations` 或等价审计表 |

## 6. 功能需求

### 6.1 历史数据浏览

- ADM-FR-01：管理后台支持选择 Vault 后查看文件列表。
- ADM-FR-02：文件列表支持按路径、删除状态、更新时间、版本号、内容哈希筛选。
- ADM-FR-03：文件详情展示当前路径、当前版本、删除状态、最近同步 checkpoint、历史版本列表。
- ADM-FR-04：版本列表展示版本号、内容哈希、作者设备、创建时间、mtime/ctime、关联同步事件。
- ADM-FR-05：支持为某个历史版本生成短期下载地址，用于人工核验内容。
- ADM-FR-05A：历史版本默认保留三个月，版本列表展示保留策略；后续版本清理必须先校验引用和备份状态。

### 6.2 误删除恢复

- ADM-FR-06：已删除文件支持从最近可用历史版本恢复。
- ADM-FR-07：恢复时可选择原路径或新路径；若目标路径已存在，必须提示冲突并要求选择覆盖、改名或取消。
- ADM-FR-08：恢复成功后，服务端必须生成新的 `restore` 或 `update` 同步事件，并推进 checkpoint。
- ADM-FR-09：客户端拉取恢复事件后，应把文件重新写回本地，并解除删除态。

### 6.3 指定历史版本为当前版本

- ADM-FR-10：未删除文件和已删除文件都可以选择某个历史版本作为当前版本。
- ADM-FR-11：指定版本为当前版本时必须创建一个新版本号，不得直接回写旧版本记录。
- ADM-FR-12：新版本的 `content_hash` 指向被选择的历史版本对象，便于保留完整审计链。
- ADM-FR-13：服务端生成新的同步事件并推进 checkpoint，各客户端通过 pull 收到该版本并覆盖本地当前文件。

### 6.4 受控删除

- ADM-FR-14：管理后台支持软删除文件，语义与客户端删除一致：设置 `deleted_at`、写入 tombstone、生成删除事件、推进 checkpoint。
- ADM-FR-15：批量删除必须先展示影响范围，包括文件数量、路径列表、最新版本、预计产生的同步事件数。
- ADM-FR-16：硬删除和对象 GC 不纳入本阶段；后续必须结合备份、保留期和审计策略单独设计。

### 6.5 推送到客户端

- ADM-FR-17：管理后台操作不得直接连接客户端；统一通过服务端生成 `change_events` + checkpoint 实现下发。
- ADM-FR-18：在线客户端可通过现有 SSE checkpoint 通知尽快触发 pull；离线客户端上线后通过 `sync/state` 和 `sync/pull` 补齐。
- ADM-FR-19：管理操作事件需要标记来源为 `admin`，客户端展示“由管理后台恢复/删除/回滚”的可读提示。

### 6.6 审计与回滚线索

- ADM-FR-20：每次管理操作记录操作人、目标 Vault、文件 ID、原路径、目标路径、原 head_version、新 head_version、操作原因、时间、结果。
- ADM-FR-21：管理操作失败不得产生半提交状态；数据库变更、事件写入和 checkpoint 推进必须在同一事务中完成。
- ADM-FR-22：后台展示操作历史，并支持按操作记录定位受影响文件和生成的 changeset。
- ADM-FR-23：回滚不是删除审计记录，而是创建一个新的反向管理操作。
- ADM-FR-24：批量恢复应有任务 ID、进度、成功/失败数量和失败项重试入口；该能力排入二期。
- ADM-FR-25：Vault 时间点恢复应以 checkpoint 快照预览为基础，执行时生成一批新的同步事件；该能力排入二期。
- ADM-FR-26：大规模恢复前应支持 Vault 维护模式，临时禁止客户端 commit、允许 pull；该能力排入二期。

## 7. 推荐数据模型补充

### 7.1 change_events 操作类型扩展

当前 `change_events.op` 仅支持 `create/update/delete/rename/move`。建议新增：

- `restore`：从删除态或历史态恢复为当前文件。
- `admin_set_current`：管理员指定历史版本为当前版本。

兼容策略：
- 客户端可先把 `restore` 和 `admin_set_current` 按 `update` 兼容处理。
- API 响应可增加 `source`、`reason`、`adminOperationId` 字段；旧客户端忽略新增字段。

### 7.2 管理操作审计表

建议新增 `admin_operations`：

```sql
CREATE TABLE admin_operations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vault_id UUID NOT NULL REFERENCES vaults(id) ON DELETE CASCADE,
  actor_user_id UUID NOT NULL REFERENCES users(id),
  operation TEXT NOT NULL,
  status TEXT NOT NULL,
  file_id UUID REFERENCES file_entries(id),
  before_json JSONB NOT NULL,
  after_json JSONB,
  reason TEXT NOT NULL,
  changeset_id UUID REFERENCES changesets(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 7.3 changesets 来源补充

建议给 `changesets` 增加来源字段：

- `source`: `device` 或 `admin`。
- `actor_user_id`: 管理后台操作人。
- `device_id` 对管理后台操作可为空，或使用系统虚拟设备；推荐允许为空并以 `actor_user_id` 表达来源。

## 8. API 草案

### 8.1 查询文件列表

`GET /admin/vaults/{vaultId}/files?query=&status=active|deleted|all&limit=50&cursor=...`

返回文件 ID、路径、head_version、删除状态、最近版本时间、最近 checkpoint。

### 8.2 查询文件详情

`GET /admin/vaults/{vaultId}/files/{fileId}`

返回当前状态、历史版本、删除墓碑、最近同步事件、管理操作历史。

### 8.3 预览管理操作

`POST /admin/vaults/{vaultId}/files/{fileId}/actions/preview`

请求包含：
- `action`: `soft_delete`、`restore`、`set_current_version`。
- `version`: 目标历史版本。
- `targetPath`: 恢复或改名路径。

返回影响范围、路径冲突、将生成的版本号和事件预览。

### 8.4 执行恢复

`POST /admin/vaults/{vaultId}/files/{fileId}/restore`

要求：
- `version`：恢复的历史版本。
- `targetPath`：目标路径。
- `reason`：操作原因。
- `confirmToken`：预览接口返回的一次性确认 token。

### 8.5 指定当前版本

`POST /admin/vaults/{vaultId}/files/{fileId}/set-current-version`

语义：创建新版本，内容等于目标历史版本，并生成可被客户端 pull 的事件。

### 8.6 软删除

`POST /admin/vaults/{vaultId}/files/{fileId}/soft-delete`

语义：等价于服务端受控发起一次删除变更。

### 8.7 查询管理操作历史

`GET /admin/vaults/{vaultId}/operations?fileId=&limit=50&cursor=...`

## 9. 服务端执行原则

管理操作必须复用同步提交的核心不变量：

1. 开启事务并锁定 `vault_sync_state` 与目标 `file_entries`。
2. 读取当前 head_version 与目标历史版本。
3. 校验路径冲突、删除状态、目标对象存在性。
4. 创建 `changesets`，来源标记为 `admin`。
5. 更新 `file_entries`。
6. 插入新的 `file_versions`。
7. 插入 `change_events`。
8. 更新 `vault_sync_state.latest_checkpoint`。
9. 写入 `admin_operations` 审计记录。
10. 提交事务后发布 SSE checkpoint 通知。

禁止直接改 `file_entries.head_version` 而不写 `file_versions`、`change_events` 和 checkpoint。

## 10. 客户端处理设计

- 插件继续以 `sync/pull` 作为唯一远端变更入口。
- 对 `restore`、`admin_set_current`，旧客户端可按 `update` 处理；新客户端可展示更明确的同步日志。
- 如果本地有未提交修改且服务端推送了管理操作，仍按现有版本冲突机制处理，生成冲突副本，不直接覆盖未提交本地编辑。
- 管理操作引发的删除也必须走 tombstone 逻辑，避免旧设备复活文件。

## 11. 管理后台页面建议

第一阶段页面：
- Vault 列表与基础统计。
- 文件历史列表：路径、状态、版本数、最近更新时间、删除状态。
- 文件详情抽屉：版本时间线、同步事件、墓碑、操作历史。
- 操作预览弹窗：展示影响范围、目标版本、路径冲突、确认语句。
- 操作结果页：展示 changeset、checkpoint、后续客户端同步状态提示。

第二阶段页面：
- 异常检测：短时间大量删除、重复内容覆盖、长期未同步设备。
- 批量恢复/批量删除。
- 管理操作报表和审计导出。

## 12. 验收标准

- ADM-AC-01：可查询 active/deleted/all 文件并查看历史版本。
- ADM-AC-02：可从已删除文件的历史版本恢复到原路径或新路径。
- ADM-AC-03：可把任意历史版本指定为当前版本，并生成新版本号。
- ADM-AC-04：恢复、指定当前版本、软删除都会推进 checkpoint，并能被客户端 pull 到。
- ADM-AC-05：路径冲突时不会静默覆盖，必须走预览和确认。
- ADM-AC-06：所有管理操作都有审计记录，可追溯操作者、原因、变更前后状态和 changeset。
- ADM-AC-07：管理操作失败时数据库不出现半提交状态。
- ADM-AC-08：旧客户端至少能按 update/delete 语义兼容处理管理操作事件。

## 14. 同类产品参考后的补强结论

- 保留策略：采用三个月默认保留期，后台展示版本和墓碑的可恢复窗口。
- 删除来源：文件详情必须能追踪删除设备、来源、changeset 和 checkpoint。
- 恢复预览：第一期展示版本、路径、contentHash、mtime/ctime、checkpoint；Markdown 文本 diff 后续增强。
- 批量恢复进度、时间点快照、Vault 维护模式放入二期，不阻塞单文件恢复闭环。

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 管理后台误操作造成大规模覆盖 | 数据损坏扩散到所有客户端 | 操作预览、二次确认、审计、备份提示、批量限流 |
| 直接修改 head_version 导致客户端无法同步 | checkpoint 与版本链断裂 | 所有操作必须生成 changeset/change_events 并推进 checkpoint |
| 旧客户端不认识新 op | 拉取失败或忽略恢复 | 新 op 提供兼容映射；必要时先用 update/delete 表达 |
| 路径冲突覆盖有效文件 | 用户数据丢失 | 预览阶段强校验，默认建议恢复到带后缀的新路径 |
| 对象已被清理 | 历史版本不可恢复 | 对象 GC 前校验引用和保留期；恢复时检测 object_blobs 与对象存储 |
